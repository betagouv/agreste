# Testing wagtail-transfer with two Docker instances

The destination **pulls** from the source: `localhost:8002` calls
`source:8001` (Docker service name).
The source never needs to reach the destination.

This procedure assumes `wagtail-transfer` is already wired into the project.

Do not use staging/production secrets. Do not add the destination to the
source's `WAGTAILTRANSFER_SOURCES`.

## Why two databases and two media volumes

Same code, two Postgres instances and two Docker volumes for media. Media
stored as local files (`S3_HOST` empty, `SF_USE_DB_STORAGE=0`) and
`DEBUG=True` so that `runserver` serves `/medias/`.

The `BASE_URL` in `WAGTAILTRANSFER_SOURCES` uses the Docker service name
(`http://source:8001/wagtail-transfer/`): containers reach each other through
the internal Compose network, not `127.0.0.1`.

## 1. Start the containers

```bash
docker compose -f docs/wagtail-transfer/docker-compose.transfer-test.yml up --build
```

This starts four services: `db_source`, `db_dest`, `source` (port 8001),
`dest` (port 8002). Migrations and `collectstatic` are run automatically by
the entrypoint.

## 2. Create superusers

In two separate terminals:

```bash
docker compose -f docs/wagtail-transfer/docker-compose.transfer-test.yml exec source python manage.py createsuperuser
docker compose -f docs/wagtail-transfer/docker-compose.transfer-test.yml exec dest python manage.py createsuperuser
```

## 3. Prepare source content

Open <http://localhost:8001/cms-admin/> with the source superuser. Publish
**a page that contains an image**.

## 4. Import

Open <http://localhost:8002/cms-admin/> with the destination superuser →
**Import** → source `source` → pick the test page → import under the home
page.

## 5. Verify

The page exists on the destination. The stored media file is a JPEG/PNG, not
HTML (`file` command, or open with Pillow). If the first bytes are
`<!DOCTYPE`, the source media URL is still wrong.

| Symptom | Likely cause |
| --- | --- |
| Chooser timeout | The `dest` container cannot reach `source:8001` — check they are on the same Compose network |
| HMAC error / 403 on the API | The `SECRET_KEY` in `WAGTAILTRANSFER_SOURCES` does not match the source's `WAGTAILTRANSFER_SECRET_KEY` |
| Corrupted image / 500 on renditions | The destination downloaded an HTML page (login/404) instead of the actual file |

## 6. Teardown

```bash
docker compose -f docs/wagtail-transfer/docker-compose.transfer-test.yml down -v
```

The `-v` flag removes the volumes (databases and media).

## wagtail-transfer configuration

The relevant environment variables are defined in
`docs/wagtail-transfer/docker-compose.transfer-test.yml`:

| Variable | source | dest |
| --- | --- | --- |
| `WAGTAILTRANSFER_SECRET_KEY` | `source-secret` | `dest-secret` |
| `WAGTAILTRANSFER_SOURCES` | `{}` | `{"source":{"BASE_URL":"http://source:8001/wagtail-transfer/","SECRET_KEY":"source-secret"}}` |

The `SECRET_KEY` in the destination's `WAGTAILTRANSFER_SOURCES` must be
**identical** to the source's `WAGTAILTRANSFER_SECRET_KEY` (`source-secret`).
The destination's own `WAGTAILTRANSFER_SECRET_KEY` (`dest-secret`) is not used
for this import: nothing should import *from* the destination.

## Docker-only gotcha: absolute media URLs

When importing an image, `wagtail-transfer` downloads the file from an
*absolute* URL generated by the **source** instance.

In Docker, the destination cannot reach `0.0.0.0`, so the source must advertise
a reachable host name. Ensure:

- Source `HOST_URL` is `source` (Docker service name)
- Destination `HOST_URL` can be `localhost` (for browser-facing URLs)
